## 五、测试过程中解决的关键技术问题

### 5.1 登录接口限流导致用例连锁失败

**现象**：首轮全部用例通过；第二轮执行时，从资料库模块开始大面积失败，
报错均为 `403 {"detail":"Authentication credentials were not provided."}`。

**分析**：直接请求登录接口，返回
`429 {"detail":"Request was throttled. Expected available in 29.0 seconds."}`。
即登录请求被服务端限流（实测连续约 15 次请求即触发），失败后未取得 Token，
后续所有请求都变成"未提供凭证"，因此报 403 —— **报错现象与真实原因不一致**。

**根因**：原实现为"每条用例新建临时账号并登录"，单轮全量产生 30+ 次登录请求，
超过服务端限流阈值。

**解决**：

1. 资源类用例改用会话级共享账号，用例隔离性由"每条用例一个独立资料库"保证；
2. `AuthApi` 增加会话级 Token 缓存，同一套账号密码只真正登录一次；
3. HTTP 客户端识别 `429`，按服务端返回的建议等待时长做有界重试；
4. 登录被限流时输出明确诊断信息，避免错误连锁扩散。

**效果**：单轮登录请求数由 30+ 降至 3，连续 3 轮全量执行稳定通过。

### 5.2 测试数据清理策略重构

**发现**：`DELETE /api2/repos/{id}/file/?p=/x.txt` 对不存在的文件同样返回
`200 "success"`，无法用状态码判断清理是否真正生效。

**解决**：放弃逐文件删除，改为在 Fixture 中整库删除（原子操作、结果确定）。

## 六、测试结论

1. 本次测试范围内 **43 条用例全部通过**，Seafile 系统在登录、账号、资料库、文件
   四个模块的核心功能与权限控制上行为符合预期；
2. 权限控制（水平越权、垂直越权）验证通过，未发现越权漏洞；
3. 发现 **4 处疑似服务端缺陷**，其中重命名接口 `reloaddir` 缺省场景严重程度为高（操作成功却返回失败），建议开发修复后回归；
4. 测试用例可重复执行、数据可完整回收，具备接入 CI 持续集成的条件。

## 七、遗留风险与建议

| 风险 | 建议 |
| --- | --- |
| 未覆盖并发场景 | 补充多用户并发读写同一资料库的用例 |
| 未覆盖大文件与断点续传 | 补充大文件上传、上传中断恢复的用例 |
| 未做性能测试 | 后续用 JMeter 补充登录、上传接口的并发性能基线 |
| 服务端登录限流影响 CI | 测试环境放开 `/api2/auth-token/` 限流，或在 CI 中降低执行频率 |
