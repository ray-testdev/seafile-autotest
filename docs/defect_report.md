# 缺陷报告

被测系统：Seafile 社区版（内网测试环境）
测试方式：接口自动化（Python + Requests + Pytest）
报告日期：2026-09-23

共记录 4 个缺陷，其中 DEF-004 严重程度为高。

复现方式：在项目根目录执行 `pytest -m defect -v`，对应用例会锁定"当前实际行为"。

---

## DEF-001 | 重命名资料库允许空名称，与创建接口校验不一致

| 项 | 内容 |
| --- | --- |
| 严重程度 | 中 |
| 接口 | `POST /api2/repos/{repo_id}/?op=rename` |
| 对应用例 | `test_rename_repo_to_empty_name` |

**复现步骤**

1. 以任意账号登录并创建一个资料库，拿到 `repo_id`；
2. `POST /api2/repos/{repo_id}/?op=rename`，表单参数 `repo_name=""`；
3. 再调用 `GET /api2/repos/{repo_id}/` 查看详情。

**预期结果**：拒绝空名称，返回 `400`，与创建接口保持一致。
（创建接口 `POST /api2/repos/` 传空 `name` 时返回 `400 {"error_msg": "Library name is required."}`）

**实际结果**：返回 `200 "success"`，资料库名称被改写为空字符串。

**影响**：资料库名称被清空后，前端列表会出现无名条目，用户难以辨认和检索；
两个接口对同一字段的校验规则不一致，也说明后端缺少统一的参数校验层。

**建议**：重命名接口复用创建接口的名称校验逻辑，允许的最短长度为 1。

## DEF-002 | 重命名不存在的文件返回非标准状态码 520

| 项 | 内容 |
| --- | --- |
| 严重程度 | 中 |
| 接口 | `POST /api2/repos/{repo_id}/file/?p=/x.txt` |
| 对应用例 | `test_rename_nonexistent_file` |

**复现步骤**

1. 创建一个资料库，不上传任何文件；
2. `POST /api2/repos/{repo_id}/file/`，参数 `operation=rename`、`newname=zzz.txt`，
   查询参数 `p=/not_exist.txt`（该文件不存在）。

**预期结果**：返回 `404`，响应体说明文件不存在。

**实际结果**：返回 `520`，响应体 `{"error_msg": "Failed to rename file: file does not exist"}`。

**影响**：`520` 不是标准 HTTP 状态码，通用客户端、网关、监控系统都无法正确归类；
调用方只能靠解析响应体文本来判断错误类型，无法按状态码做统一异常处理。

**建议**：改用 `404`。

## DEF-003 | 删除不存在的文件也返回 200

| 项 | 内容 |
| --- | --- |
| 严重程度 | 低 |
| 接口 | `DELETE /api2/repos/{repo_id}/file/?p=/x.txt` |
| 对应用例 | `test_delete_file_is_idempotent_with_200` |

删除一个文件后，对同一路径再删一次，仍然返回 `200 "success"`，而不是 `404`。

影响主要在自动化侧：没法用状态码判断脏数据到底清干净了没有。
本项目的清理策略因此改成在 Fixture 里整库删除，不再依赖逐文件删除。
建议区分"删除成功"和"目标不存在"两种返回。

## DEF-004 | 不传 reloaddir 时，重命名已生效却返回 404 且响应体为 HTML

| 项 | 内容 |
| --- | --- |
| 严重程度 | **高** |
| 接口 | `POST /api2/repos/{repo_id}/file/?p=/x.txt` |
| 对应用例 | `test_rename_without_reloaddir_returns_404_but_succeeds` |

**复现步骤**

1. 创建资料库，上传一个文件，服务端路径为 `/a.txt`；
2. 调用重命名接口，参数 `operation=rename`、`newname=b.txt`、`p=/a.txt`，
   **不传 `reloaddir`**（该参数可选，缺省为 `false`）；
3. 记录响应状态码与 `Content-Type`；
4. 分别查询 `/a.txt` 与 `/b.txt` 的文件详情，确认文件到底改名了没有。

**预期结果**：返回 `200`，响应体为 JSON，表示重命名成功。

**实际结果**

| 观测项 | 实际值 |
| --- | --- |
| 状态码 | `404` |
| Content-Type | `text/html; charset=iso-8859-1`（Apache 风格 HTML 错误页，**不是 JSON**） |
| `GET /a.txt` | `404` —— 旧文件名已不存在 |
| `GET /b.txt` | `200` —— 新文件名已存在 |
| 再对 `/a.txt` 调一次重命名 | `520 {"error_msg": "Failed to rename file: file does not exist"}` |

即：**重命名实际已经成功，接口却返回失败**。

显式传 `reloaddir=false` 结果相同；传 `reloaddir=true` 则返回 `200` + JSON，一切正常。

> 该缺陷最初是在按接口文档手工调试时发现的：请求返回失败，但去客户端界面查看，
> 文件其实已经改名成功，且响应体是 HTML 而非 JSON，导致断言失败。

**影响**

1. **客户端与服务端状态不一致**：调用方依据 404 认为重命名失败，会继续按旧文件名操作，
   而服务端上文件已是新名字 —— 属于数据一致性问题；
2. **响应体不是 JSON**：客户端若直接 `response.json()` 解析会抛异常；
   只能靠状态码兜底，而状态码恰好是错的；
3. **重试会恶化**：按常规做法重试，第二次会拿到 `520`，错误信息变成"文件不存在"，
   进一步误导排查方向；
4. `reloaddir` 是可选参数且缺省为 `false`，**任何未显式传该参数的调用方都会踩到**，影响面较大。

**规避方式**：调用时显式传 `reloaddir=true`。

**建议**：修复 `reloaddir=false` 分支的响应处理，统一返回 `200` + JSON；
无论该参数取值如何，都不应改变"操作是否成功"的返回语义。

## 附：接口设计观察（非缺陷）

| 观察点 | 说明 |
| --- | --- |
| 字段命名不一致 | 创建资料库返回 `repo_id`，而资料库**列表**接口中同一字段叫 `id` |
| 401 与 403 混用 | Token 非法返回 `401`，完全不带 Token 却返回 `403`（常规语义应为 `401`） |
| 登录接口限流 | `/api2/auth-token/` 短时间约 15 次请求即触发 `429`，接口测试需做登录复用 |
| 账号删除返回 `202` | 删除不存在的账号返回 `202 Accepted`，而非 `404`；属可接受的设计，但需在用例中锁住 |
